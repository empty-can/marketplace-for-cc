## 0. 要約

- 扱う手法は、設計書の 4 手法（C、B、A、probe）と証跡上の `manual` の 5 つ。加えて、現行の設計に無いが必要になりうる手法を 4 つ挙げた（発火テスト、スクリプト単体テスト、環境の事実確認、利用実績の観測）
- 各手法を「目的・確認観点・評価内容・自動化可否・実施タイミング」で整理した（2 節）。手法の違いは、何を確かめるか、隔離の強さ、モデルの役割の 3 つの軸でほぼ説明できる（1 節）
- 設計書 v3.3 の構成は、手法を証跡の最下層に置いたので手法の追加に強い。一方で、手法の特性とずれる箇所と、拡張の受け皿が無い箇所を 15 件挙げた（4 節）。段階 1〜4 の実装前に決めないと手戻りが出るのは M1、M3、M6、M9、M10、M14 の 6 件
- 検討メモの方針のうち 1 点は修正を提案する。「採点者は被験者より強いモデルにする」には docs の裏付けが無い。docs が求めるのは採点者の固定で、CI の例は被験者より弱い採点者を使う（1-2）
- 実測で 2 つの事実が加わった。skill-creator の description 最適化（発火テスト）の同梱スクリプトは、このマシンでは動かない（2-3）。probe の init イベントから、読み込まれた skill と Plugin の一覧、memory の保存先が取れる（1-3）

## 1. 整理に使う 3 つの軸

### 1-1. 何を確かめるか

docs は skill の確認を「起動したか」と「起動した後に意図どおり動いたか」に分け、別々に測るよう求める（45333 行「Seeing a skill trigger tells you Claude found it, not that it did what you intended」）。また、作成時の文脈が指示の不足を隠すので、新しいセッションで確かめるよう求める（45335 行）。本書はこれに構造、副作用、環境の前提を加えて 5 つの観点に分ける。

| 観点 | 内容 | 例（pre-compact） |
|---|---|---|
| 構造 | Plugin が Claude Code に読み込まれる形か。決定的 | `plugin.json` のスキーマ、SKILL.md の frontmatter |
| 発火 | 起動すべき依頼で起動し、起動すべきでない依頼で起動しないか | 「pre-compact を実行して」で起動し、「今日はここまで」では手順を実行しない |
| 出力と手順 | 起動した後の最終応答、ツールの使い方、作成物が期待どおりか | 途中テキストを出さない、終了方式を判定する、`/compact` コメント案の 4 条件 |
| 副作用 | git、memory、ファイル、権限の境界への影響 | 未コミット変更を報告し、承認なしにコミットしない。memory の書き方 |
| 環境の前提 | Plugin ではなく Claude Code 自体の挙動。設計書 2 節の F 根拠 | 非対話モードの文中起動（F21）、`autoMemoryDirectory` の効き方（F35、F36） |

発火には起動の経路が 3 つある。先頭のスラッシュ（ユーザー起動）、Skill ツール（モデル起動）、文中のスラッシュ表記（F21）。pre-compact は本文の先頭に実行ゲートを持つ（`plugins/pre-compact/skills/pre-compact/SKILL.md` 17 行）。このため「Skill ツールが呼ばれた」と「本文の手順が実行された」が一致しない。否定のテストは「呼ばれない」か「呼ばれてもゲートの 1 行で終わる」のどちらでも合格になる。

### 1-2. モデルの役割

検討メモ 2-2 の整理（被験者と、採点者・実行者）を維持する。補足が 2 点ある。

- **採点者は「固定」が本質で、「被験者より強い」は手法による（判断）。** docs は CI で両モデルを固定するよう求める（32150 行）。ただし例は被験者が `claude-sonnet-5`、採点者が `claude-haiku-4-5` で、採点者のほうが弱い（32152〜32160 行）。docs の注意は「小さい採点モデルは書式の違いで正答を誤判定しうる。疑わしければ `--judge-model sonnet` で再実行し、rubric を具体的にする」（31989 行）で、採点者を被験者より強くすることは求めていない。B の `llm` grader は短い出力と具体的な PASS / FAIL 条件で使う前提（31985〜31987 行）なので、中位のモデルで足りうる。一方、A の採点者・実行者は記録を読んで質的に判定し、改善案を書く。作業指示者の指摘どおり、ここは性能が要る。なお、検討メモが挙げた「被験者と同じモデルで採点すると自己評価の偏りが出る」は、採点者を被験者と別のモデルにする理由として残る。強さの上下とは別の論点である
- **B の採点者の既定は「バックグラウンド処理に使うモデル」（31981 行）で、Haiku 級を指す**（662 行、26282 行）。省略すると、Claude Code の版で変わりうる値になる。検討メモ 2-1 の「既定値は利用条件ですらない」は採点者にも当てはまる

### 1-3. 隔離の強さ

| 段 | 手法 | 読み込まれるもの | 帰結 |
|---|---|---|---|
| 0 | C | モデルを使わない | 環境に依存しない |
| 1（最も強い） | B | 対象 Plugin だけ。ユーザー設定、hooks、`CLAUDE.md`、MCP、他の Plugin、memory、skill は無い（32250 行） | 再現性が高い。実利用の条件（他の skill との競合、memory、git）は測れない |
| 2 | probe、A の run | 新しい cwd と git、専用の memory。ユーザー設定と、そこで有効な Plugin、ユーザー直下の skill は読み込まれる（F34、F42） | 実利用に近い。条件を記録しないと再現しない |
| 3（最も弱い） | manual | 2 と同じ構成の対話セッション。操作者が途中で介入できる | 対話でしか起きない挙動を見られる。再現は手順書頼み |

発火は他の skill との競合に左右される。skill が多いと、description は一覧の文字数予算に合わせて切り詰められ、照合に要る語が落ちうる（41769 行、45600 行）。B には対象 Plugin しか無いので、この競合は起きない。発火の測定値は、B では「競合が無い条件」、probe では「作業指示者の環境の条件」を表す。

実測（2026-10-12。元セッションの一時領域の `probe/gate/pos.jsonl`、ゲート方式の肯定テスト）: init イベントは `model`（`claude-sonnet-5-5`）、`skills`（36 件。`pre-compact:pre-compact` と `skill-creator:skill-creator` を含む）、`plugins`（`pre-compact@inline` を含む 5 件と、それぞれの `version`、`source`）、`memory_paths.auto`（サンドボックスの `memory/`）、`claude_code_version`（`2.1.296`）を持つ。effort の値は無く、`per_turn_effort_active: true` だけがある。記録の全イベントを見ても、effort の値を持つキーは無い。result イベントは `total_cost_usd`、`modelUsage`、`permission_denials` を持つ。

## 2. 手法ごとの整理

自動化可否は 4 つの段階ごとに書く。実行（起動して記録を残す）、判定（期待項目の合否）、集計（run をまたいだ数値）、判断（結論と改善）。「自動」は、スクリプト 1 本で人が介在せずに終わることを指す。

### 2-3. A: skill-creator

skill-creator は 5 つの機能をまとめた Plugin で、機能ごとに手法としての性質が違う。docs の紹介（45344〜45364 行）と同梱の `SKILL.md` から整理する。

| 機能 | 目的 | 判定するもの | 本設計での扱い |
|---|---|---|---|
| A-1 静的レビュー | SKILL.md の書き方の問題を見つける（指示が届く位置、曖昧さ、トークン量） | A のセッションの Claude | `report.md` に書く。前回の報告書の「静的レビュー」8 件がこれにあたる |
| A-2 with / without の評価 | skill の有無で pass rate、時間、トークンがどう変わるか | 機械判定と、A のセッションの Claude か人 | run をハーネスで実行し（採用理由 14）、判定は 7-3、集計とビューアは同梱のもの（8-1） |
| A-3 改善ループ | 指摘を受けて skill を直し、次の iteration で効果を確かめる | 人（ビューアのフィードバック）と Claude | 改訂は新しい断面と試行になり、iteration は 1 から振り直す（3-2）。旧版を基準にする `old_skill` 腕は無い（M5） |
| A-4 ブラインド比較 | 2 つの版の出力を、どちらの版か伏せて独立の agent に比べさせる | comparator と analyzer の subagent | 置き場が無い。任意の機能なので当面は不要（判断） |
| A-5 description 最適化 | 発火の正確さを上げる。should-trigger と should-not-trigger の query 約 20 件を各 3 回実行し、6 対 4 で学習用と検証用に分け、最大 5 回改善する | 機械（Skill ツールか Read の呼び出しの有無） | 置き場が無い。同梱スクリプトはこのマシンでは動かない（下記、M4） |

| 項目 | 内容 |
|---|---|
| 目的 | skill が役に立っているか、どこを直すべきかを見つける。評価より改善のための手法（検討メモ 3 節） |
| 確認観点 | 出力と手順（A-2）、書き方（A-1）、発火（A-5）。人のレビューで主観的な品質も見る |
| 評価内容 | `evals.json` の prompt と expectations。`grading.json` の合否と根拠、`benchmark.json` の pass rate・時間・トークンの平均と標準偏差、ビューア上の人のフィードバック。前回は with 3 run、without 2 run で、報告書自身が「ばらつきの評価には少ない」と書いている |
| 自動化可否 | 実行は自動（ハーネス）。判定は半自動（`auto_checks` の範囲だけ機械、残りは Claude か人）。集計は自動（同梱スクリプト。`-X utf8` が要る。F39）。判断（改善案と採否）は人。全体を対話セッションが主導するので、無人では回らない |
| 実施タイミング | 新規 skill の作成時と大きな改訂時（`feature`）、問題の調査時（`investigation`）。費用と人手がかかる（前回は本番 15 run で約 4.0 ドル）ので、`maintenance` の毎回には向かない（判断） |
| 被験者 | 各 run（7-2 の `-Model`、`-Effort`） |
| 採点者・実行者 | A のセッション自体のモデル。作業指示者が起動時に選ぶ。証跡に残らない（M3） |

A-5 の同梱スクリプト（`scripts/run_eval.py`）の性質。

- 対象 skill の description を一時的なコマンドファイルにして、cwd から上へ最初に見つかった `.claude/` の `commands/` に書き、`claude -p` に query をそのまま渡す。終われば消す（52〜66 行、178〜181 行）。Plugin を読み込まない（`--plugin-dir` を付けない）ので、測るのは description の文面であり、名前空間付きの Plugin の skill としての発火ではない
- permission mode を明示せず、`--model` も任意。ユーザー設定を継承する（F34）ので、インストール済みの対象 Plugin があれば本物の skill と一時コマンドが並ぶ
- パイプに `select.select` を使う（108 行）。**このマシンの Python 3.14.3 では、パイプに対する `select.select` が `OSError`（WinError 10093）で失敗した**（実測 2026-10-12）。Python の `select` は Windows ではソケットにしか使えない。したがって A-5 は、ネイティブ Windows ではそのままでは動かない
- コマンドファイルを文字コードの指定なしで書く。`-X utf8` が無いと cp932 で書かれる（F39 と同じ問題）
- description の改善（`improve_description.py`）も `claude -p` を呼ぶ。API キーは要らない

### 2-4. probe（`claude -p` ハーネス）

| 項目 | 内容 |

### 4-3. 各項目

#### M1. 被験者条件の層が無い（特性、実装前）

- **現状**: 試行の `model` / `effort` は最初の実行の値で、以後変えない（R4）。各実行にも記録されるが、同じ試行に別のモデルの実行を追加しても拒否しない。probe の run は `<case>/<config>/run-<k>/` に条件の区別なく積まれる
- **問題**: 下限と代表点の 2 点を同じ試行で実行すると、集計で 2 つの条件が混ざる（skill-creator の集計は腕ごとに平均する）。また、最初の実行が C（モデルを使わない）の試行では、試行の `model` が null のまま固定される。10 節の段階 2 はまさに C から試行を作る
- **変更候補**: 検討メモ 2-4 の「1 試行 = 1 被験者条件」を採る。
  1. 試行の `model` / `effort` を「被験者条件」と定義し直す
  2. 値は「モデルを使う最初の実行」で確定する。C と、`-Model` を渡さない 7-6 では確定しない
  3. 確定した後、違う `-Model` / `-Effort` の実行を同じ試行に追加しようとしたら、共通処理の前に拒否する（R7 の順序。7-1、7-2、7-4、7-6）
  4. B は effort を渡せないので、`model` だけを照合する（M11 の結果で見直す）
  5. 条件をまたぐ比較は、改訂前後の比較と同じく試行どうしで行う（3-2）
