## 1. 作業指示者の決定と問題提起

- 論理 I3、実用 I-3・I-5 は推奨案のとおり採用で確定（態度表明は未記入。I4 の方向が決まった時点で 1.0 版にまとめて記入する）。
- I4 は採用内容を保留。指摘の根本には、設計書の一段上位の観点（「Plugin の一連のテストを実施するに当たっての考え方・フロー」）がスコープ外になっていたことがある。レビューの不足ではなくスコープ設定の帰結。
- 「考え方・フロー」の全体は実運用しながら整備するとしても、仕組みで指定が必須の項目（モデル、effort）の決め方は、仮でも無いと仕組みを動かせない。
- 「日常のセッションのモデルと effort」は基準にならない。pre-compact のような汎用 skill は Haiku 以外の全モデル・大半の effort で実行されうるので一意にならない。全組み合わせは不要だが、1 パターンで十分と言える情報も無い。
- 手法の性質（skill-creator は Skill なので実行するモデルに性能が要る）と Plugin の規模・性質（pre-compact、win-file-encoding、文書執筆・レビュー skill、`workflow.js` を含む大規模 skill）で、求められるモデルは変わる。

## 2. Fable の見解（I4 への回答）

### 2-1. 補足

- ユーザー設定の値は恣意的ではなく、利用者が作業指示者本人である以上「事実上の利用条件」。保証が無いのは値ではなく「選んだ理由と時点が記録されない」こと。
- Claude Code の既定値は利用条件ですらない。B（plugin eval）は一時ホーム（F25）なので `--model` を省くと既定値になる。同じ問いは B の `--model` と `--judge-model` にも及ぶ。
- 開発は止まらない（段階 2〜6 は任意の値で動く）。止まるのは段階 7 以降の本物の活動。

### 2-2. モデルの役割は 2 つ

| 手法 | 被験者（Plugin を動かすモデル） | 採点者・実行者（テストを動かすモデル） |
|---|---|---|
| A: skill-creator | 各 run の `claude -p`（7-2 の `-Model` / `-Effort`） | A のセッション自体。skill-creator を実行し、判定 JSON と報告書を書く |
| B: plugin eval | `--model` | `--judge-model` |
| C: validate | 無し（決定的） | 無し |
| probe | 各 run | 手動判定を書く Claude か作業指示者。機械判定にモデルは無関係 |

- 採点者・実行者はテストの基盤。「条件」ではなく「固定値」として活動をまたいで同じにする。docs の CI 例も比較可能性のため両モデルを固定するよう案内（32048 行付近）。被験者と同じモデルで採点すると自己評価の偏りが出るので、被験者より強いモデルを固定する。
- 被験者だけが「テスト条件」。

### 2-3. 被験者の条件は「利用範囲」から 2 点を選ぶ

- Plugin ごとに「利用範囲」を宣言する（例: pre-compact は Haiku 以外の全モデル × 各モデルの全 effort。文書執筆・レビュー skill は Opus 5.5 / Fable 5.1 の high 以上。`workflow.js` を含む大規模 skill はオーケストレータが Opus 5.5 high で配下は skill 側が指定）。範囲を決めるのは Plugin の作者（作業指示者）。仕組みは記録する。
- 範囲の中から **下限**（最も弱いモデル × 最も低い effort。effort の選択肢はモデルで違うので角の点）と **代表点**（最もよく使う条件）の 2 点を選ぶ。
- 下限を選ぶ理由: skill は自然言語の指示で、崩れるとすれば弱い側。単調性は概ね成り立つが、強いモデルが手順を「不要」と判断して省く逸脱もあるので代表点を併せる。
- 「1 パターンで十分か」は証跡で確かめる。初回（`feature` / `release`）は 2 点、下限と代表点の結果が揃う実績が溜まったら `maintenance` は下限だけに減らす。下限で落ちたら、それが実際の利用範囲の境界で、README の「テスト済み条件」になる。
- 再テストの契機: 利用モデルの変更、Claude Code の既定モデルの変更、Plugin の改訂。
- 閉じ方: Plugin の CHANGELOG / README に「テスト済み条件」を書き、宣言した条件をテストする。

### 2-4. 仕組みへの影響（v3.3 からの変更候補。未反映）

- 現行の証跡構造には被験者条件の層が無い（`probe/<case>/<config>/run-<k>/` に別モデルの run が混ざる）。最小の変更は「1 試行 = 1 被験者条件」と定め、試行の `meta.json` の `model` / `effort` を条件として扱い、同じ試行への追加実行で条件が違えば拒否する。条件間の比較は試行どうしの比較。
- 採点者・実行者の固定値と、Plugin の利用範囲（2 点の定義）は活動か Plugin 側のプロファイルに持ち、7-1・7-2・7-4 の省略時既定をそこから取る。I4 の採用内容（`-Model` / `-Effort` の必須化と環境変数）はこの形に置き換わる。
- C は無関係。B は `--model` と `--judge-model` を同じ考え方で埋める。
- 具体値（利用範囲、採点者の固定値）は作業指示者が決める。候補: 主条件は現在の日常利用（ユーザー設定の `sonnet` が解決する完全 ID と `modelSettings` の effort）、比較条件は Opus 5.5 の high（移行データと同じ）。

## 3. 4 手法の一覧（何を確かめる手法か・評価できる観点・制約・モデルの関わり）

| 手法 | 何を確かめる手法か | 評価できる観点 | 評価できないこと・制約 | モデルの関わり |
|---|---|---|---|---|
| **C: `claude plugin validate --strict`** | Plugin が Claude Code に正しく読み込まれる形か。配布物の構造検証 | `plugin.json` と `marketplace.json` のスキーマ、skill / agent / command の frontmatter の構文、hooks モジュールの構文と危険な書き方、`.mcp.json` で読み込み時に落ちるエントリ、コンポーネントのパスが Plugin 外を指していないか、名前の制約。`--strict` で警告も失敗（docs 78829 行〜） | skill 本文の内容や挙動は見ない。Plugin ルートの `SKILL.md` は読まない。Marketplace から実行したときは各 Plugin の中身を開かない。決定的 | 無し |
| **B: `claude plugin eval`** | 隔離された環境で、Plugin ありと無しで応答がどう変わるか。回帰 suite として固定 case を機械採点 | with / without の差（`meanDelta`）、閾値による合否、最終応答・トレース・作成ファイル・ファイル内容に対する `regex` / `llm` / `tool_used` / `tool_order` / `file_exists` / `baseline` grader（docs 32338 行〜）、会話の続きからの挙動（`context.history_file`。F29）、MCP のモック。終了コードで CI に組める（F37） | 一時ホームでユーザー設定・`CLAUDE.md`・memory・他 Plugin を読まず、Bash ツールが無い（F25）。Windows では Bash / PowerShell を許可した case は全滅（F26）。`tool_used: Skill` はスラッシュ起動を数えない（F27）。without 腕に先頭スラッシュの prompt は渡せない（F28）。git や memory に触れる手順、権限まわり、実環境の挙動は測れない | 被験者 = `--model`（省略時は既定。継承なし）、採点者 = `--judge-model` |
| **A: skill-creator** | skill が役に立っているか、どこを直すべきか。改善ループのための評価 | with / without の pass rate・時間・トークンの平均と標準偏差、iteration 間の変化、人のレビュー（ビューア）、分析者パス、ブラインド比較（任意）、発火の正確さ（description 最適化。should-trigger / should-not-trigger の query。現行 suite には未組込） | 標準方式は run を subagent で動かすため隔離と記録が弱く、本設計では run を probe ハーネスに置き換えている（採用理由 14）。採点の正本は人の判定で、機械判定は `auto_checks` の範囲だけ。再現性より改善の洞察に向く | 被験者 = 各 run、採点者・実行者 = A のセッションの Claude |
| **probe（`claude -p` ハーネス）** | 実環境に近い条件で個別の挙動が期待どおりか。B で測れない項目の補完 | git init 済み `repo/` と専用 `memory/` を使う手順、文中起動の可否（F21）、`acceptEdits` と `--add-dir` 下の権限拒否（F11、F41）、途中テキストの有無、最終応答の構文、費用と時間。`stream-json` の全記録が残る | ユーザー設定を継承（F34、F42）するので隔離は B より弱く、条件を明示しないと再現しない。`llm` 判定器は無い。case 定義は自作なので網羅性は設計者次第 | 被験者 = `-Model` / `-Effort`、採点者 = 手動判定を書く Claude か作業指示者 |

### 方向性への含意

- C はモデルに依存しない。毎回・無条件で実行する。
- B・A・probe は被験者モデルに依存し、B と A は採点者モデルにも依存する。「役割を 2 つに分ける」整理は 3 手法に共通。
- B は隔離が強い代わりに測れる範囲が狭い。pre-compact のように git と memory に触れる skill の中核手順は B では検証できない。B の価値は応答の形の回帰検知と CI での自動実行。
- probe は測れる範囲が広い代わりに環境依存。被験者条件の明示と記録が最も効く手法。
- A は評価より改善の手法。同じ条件で繰り返して回帰を見る用途には B と probe が向く。
- 発火テストが現行 suite に無い。skill-creator の description 最適化は別種のテスト。pre-compact は `disable-model-invocation` を外した（F21）ので、自発起動しないこと・依頼時に起動することの両方が品質に関わる。B の `tool_used: Skill` でモデル起動は測れるがスラッシュ起動は測れない（F27）。
- 被験者条件の設計は「C 以外の 3 手法に共通の条件（下限と代表点）」として一つに決めてよい。手法ごとに違うのは採点者の固定値。

## 4. 本 branch の目的（作業指示者の指示、2026-10-12）

上の一覧を出発点に、各テスト手法について **確認観点・目的・評価内容・自動化可否・実施タイミング** を整理し、作業指示者が正確に把握できる形にする。そのうえで、設計書 v3.3 のフォルダ構成とスクリプトが、各手法の特性に沿い、かつ将来の拡張性（手法の追加、発火テスト、被験者条件の層）を持つ構成・内容になっているかを確認する。整理結果は、元セッション（review-by-fable。設計書とレビューの文脈を保持）へそのまま入力する。
