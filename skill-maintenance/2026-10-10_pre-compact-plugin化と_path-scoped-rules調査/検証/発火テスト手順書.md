# path-scoped rule / paths: 付き skill / 入れ子 CLAUDE.md の発火テスト手順書

2026-10-10 に Claude Code 2.1.296（Windows 11、Git Bash、auto モード、モデル Fable 5.1）で実施した検証の再現手順。結果は `発火テスト結果_2026-10-10.md` を参照。

## 検証の原理

- path-scoped rule・入れ子 `CLAUDE.md` は、発火すると **Claude のツール結果の直後に system-reminder として本文が注入される**（`Contents of <path>:` で始まるブロック）。Claude 側からは「ツール結果に rule 本文が付いてきたか」で発火を判定できる
- `paths:` 付き skill は、発火すると **本文ではなく「The following skills are available for use with the Skill tool: - <name>: <description>」という一覧追加の通知**が届く
- したがって検証は **Claude Code のセッション内で Claude 自身がツールを実行し、結果に注入が付くかを観察する**形で行う。シェルスクリプト単体では検証できない（注入はハーネスが Claude 向けに行うため）

## 前提知識（検証設計に影響する既知の挙動）

| 挙動 | 影響 |
|---|---|
| rule は **1 セッションに 1 rule 1 回**しか注入されない | 1 つの rule で複数のアクセス方法を試すと、2 回目以降は必ず陰性に見える。**テストごとに別の rule を割り当てる** |
| 入れ子 `CLAUDE.md` も **1 ディレクトリ 1 回** | 同上。ディレクトリを分ける |
| `paths:` 付き skill の通知も 1 skill 1 回 | 同上。skill を分ける |
| セッション途中に追加した rule は即座に有効（検証済み） | fixture をセッション中に作ってよい。ただし **新規 skill は Skill ツールの登録更新を待つ必要がある**（作成直後は `Unknown skill`。Read 等を契機に更新される） |
| 発火済み rule を編集しても再注入されない（検証済み） | 本文を変えて再テストしたいときは新しい rule を作る |
| 発火には陽性対照が必須 | 「不発」を結論にする前に、同じ rule を確実に発火する方法（単一 `head`、Read、Write）で叩き、rule が生きていることを確認する |

## 手順

1. リポジトリルートで fixture を作る: `bash skill-maintenance/<本フォルダ>/scripts/setup-rule-probe.sh`
   - rule A〜F（`**/*.pA` … `**/*.pF`）、`paths:` 付き skill、対照 skill、入れ子 CLAUDE.md（2 階層）が作られる
2. Claude に、以下の各テストを **別々のツール呼び出しで** 実行させ、ツール結果に注入が付いたかを記録する。1 テストに 1 rule（1 拡張子）を割り当てる

| # | 対象 rule | Claude に実行させる操作 | 判定 |
|---|---|---|---|
| T1 | rule A | Bash: `cat <abs>/.tmp-probe/t.pA`（単独） | A 本文が付けば発火 |
| T2 | rule B | Bash: `cd <repo> && cat .tmp-probe/t.pB`（`&&` 連結） | B 本文 |
| T3 | rule C | Bash: `cd <repo> && head -1 .tmp-probe/t.pC && echo done`（3 連結） | C 本文 |
| T4 | rule D | Bash: `cat <abs>/.tmp-probe/t.pD \| head -1`（パイプ） | D 本文 |
| T5 | rule E | Bash: `sed -i 's/target/edited/' <abs>/.tmp-probe/t.pE`（Bash 編集） | E 本文 |
| T6 | rule F | Grep ツール: pattern `target`, path `<abs>/.tmp-probe/t.pF`, output_mode content | F 本文 |
| T7 | T4〜T6 の陽性対照 | 陰性だった rule について Bash: `head -1 <abs>/.tmp-probe/u.p<X>`（単独）または Write ツール | 本文が付けば rule は生きていた＝陰性は本物 |
| T8 | 入れ子 CLAUDE.md | Bash: `cd <repo> && cat .tmp-probe/nested/sub/deep/f.txt` | L1 と L2 の両方の本文が付けば祖先探索込みで発火 |
| T9 | paths 付き skill | Bash: `cat <abs>/.tmp-probe/s1.sP`（単独） | 「skills are available」通知が出るか |
| T10 | paths 付き skill | Read ツール: `<abs>/.tmp-probe/s2.sP` | 同上（T9 が陰性なら陽性対照） |
| T11 | 直接起動 | Skill ツール: `<prefix>-skill-paths`（T9/T10 より前に、未サーフェスの状態で） | `Unknown skill` か起動か |
| T12 | 直接起動の対照 | Skill ツール: `<prefix>-skill-plain` | 起動すれば登録更新は済んでいる |
| T13 | ユーザー入力相当 | シェル: `MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*' claude -p "/<prefix>-skill-paths" --max-turns 3` | 本文センチネルが返るか。**Git Bash では `MSYS_NO_PATHCONV=1` が無いと `/name` が `C:/Program Files/Git/name` に変換される** |
| T14 | rule の途中追加 | セッション中に新しい rule を作ってから対象を `cat` | 発火すれば起動時列挙ではない |
| T15 | rule の編集 | 発火済み rule の本文を `sed -i` で書き換え、別の対象ファイルを `cat` | 新本文が付かなければ 1 セッション 1 回の重複排除 |

3. 終了後に消す: `bash skill-maintenance/<本フォルダ>/scripts/cleanup-rule-probe.sh`、`git status` が clean であることを確認

## 注意

- Write ツールで `.ps1` 等を作ると本リポジトリの PostToolUse hook（文字コード検査）が差し戻す。これは検証の邪魔にはならず、むしろ「rule 本文が hook より後に届く」ことの観察材料になる
- `claude -p` は非対話モードであり、対話 TUI での `/name` 入力と完全に同じ経路とは限らない。T13 の結果は「`-p` モードで未登録」までが事実
- 検証はハーネス（Claude Code）側の挙動なので、結果はモデルのバージョンではなく **Claude Code のバージョン**に依存する。再検証時は `claude --version` を記録する
